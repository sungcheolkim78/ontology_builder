# Ontology Builder Product Requirements

> 이 문서는 제품 기능의 기준 문서다. 현재 구현과 테스트가 보장하는 동작을
> 요구사항으로 정의하며, `docs/SPEC.md`와 코드 주석은 보충 설명으로 본다.
> 미구현 항목은 요구사항이 아니라 `향후 범위`에 둔다.

## 1. 제품 개요

Ontology Builder는 문서를 업로드하면 문서에 맞는 온톨로지 스키마를 만들고,
그 스키마로 엔티티와 관계를 추출해 지식 그래프로 저장하는 웹 애플리케이션이다.
사용자는 그래프를 시각적으로 검토하고, 문서와 그래프를 근거로 하는 GraphRAG
채팅을 통해 문서 내용을 탐색한다.

핵심 가치:

- 긴 문서를 노드·엣지·타입이라는 검토 가능한 구조로 바꾼다.
- 스키마와 그래프를 재사용·검증·진화시켜 반복 작업의 품질을 높인다.
- 답변에 사용한 타입과 관련 노드를 UI에서 그래프로 역추적할 수 있게 한다.

## 2. 사용자와 사용 사례

주 사용자는 문서 집합을 분석하고 지식 구조를 설계하는 개발자, 연구자,
도메인 전문가다. 현재 제품은 단일 공유 데이터 공간을 전제로 하며, 사용자별
계정·권한 모델을 제공하지 않는다.

### 기본 사용 흐름

1. PDF, Word, PPT, CSV 등 지원 형식의 문서를 업로드한다.
2. 시스템이 문서를 Markdown으로 변환하고 원본 파일명을 보존한다.
3. 문서에서 스키마를 생성하거나 기존 문서/도메인 스키마를 선택한다.
4. 스키마에 따라 노드와 엣지를 추출하고 임베딩을 생성한다.
5. 그래프, 스키마 미리보기, 원문을 함께 검토한다.
6. 문서에 질문하고 답변에 표시된 관련 타입·노드로 그래프를 탐색한다.
7. 필요하면 검증 보고서를 만들고 스키마 진화안을 적용하거나 새 버전을 활성화한다.

### 고급 사용 사례

- 문서 자체의 후보 클래스·관계 구조를 먼저 discovery한다.
- 여러 문서의 스키마를 순차적으로 수렴해 도메인 스키마를 저장한다.
- 반복 스키마 생성의 안정성과 중복 타입을 측정한다.
- 같은 스키마를 여러 문서에 적용하고 문서별 그래프를 버전으로 관리한다.

## 3. 제품 범위

### 3.1 문서 관리 및 변환

**FR-DOC-01** 시스템은 multipart `file` 업로드를 받아 파일을 문서 식별자에
안전하게 매핑해야 한다.

**FR-DOC-02** Markdown 파일은 재변환하지 않고 UTF-8 텍스트로 등록해야 한다.

**FR-DOC-03** 그 외 지원 형식은 `anydoc`를 이용해 Markdown으로 변환해야 한다.
변환 실패, 지원하지 않는 확장자, 잘못된 Markdown 인코딩은 HTTP 400으로
반환해야 한다.

**FR-DOC-04** 출력 파일은 `{stem}_raw.md` 형식으로 저장하고, 업로드 당시의
원본 파일명은 문서 manifest에 보존해야 한다.

**FR-DOC-05** 사용자는 저장된 문서 목록을 최신 수정 순으로 보고, 문서 원문을
읽을 수 있어야 한다. 목록에는 스키마·그래프 존재 여부가 포함되어야 한다.

### 3.2 스키마 설계

**FR-SCHEMA-01** 시스템은 문서 텍스트와 문서 유형을 LLM에 전달해
`node_types`와 `edge_types` 스키마를 제안해야 한다.

**FR-SCHEMA-02** 사용자는 discovery 보고서를 별도로 실행하고 조회할 수 있어야
한다. discovery는 문서별 최신 보고서 하나를 저장하며 스키마 버전과 독립적이다.

**FR-SCHEMA-03** 사용자는 discovery 결과를 스키마 생성 프롬프트에 선택적으로
포함할 수 있어야 한다.

**FR-SCHEMA-04** 사용자는 다른 문서의 활성 스키마를 복사하거나 저장된 도메인
스키마를 문서의 새 버전으로 적용할 수 있어야 한다.

**FR-SCHEMA-05** 스키마를 저장할 때 문서별 단조 증가 버전을 만들고 새 버전을
활성화해야 한다. 각 버전은 문서 유형과 생성 시각을 기록해야 한다.

**FR-SCHEMA-06** 사용자는 버전 목록 조회, 특정 버전 활성화, 버전 삭제를 할 수
있어야 한다. 활성 버전 삭제 시 남은 버전 중 가장 큰 버전을 활성화한다.

**FR-SCHEMA-07** 사용자는 같은 문서에 대해 스키마 생성 결과의 안정성을 여러
회 측정하고, 도메인 스키마 후보의 중복 타입을 임계값으로 탐지할 수 있어야 한다.

### 3.3 그래프 추출과 저장

**FR-GRAPH-01** 추출은 활성 스키마를 사용해야 한다. 활성 스키마가 없으면
일반 `Entity`/`RELATED_TO` 기본 스키마를 새 버전으로 만든 뒤 진행한다.

**FR-GRAPH-02** LLM은 스키마에 맞는 `nodes`와 `edges`를 반환해야 하며, 노드와
엣지는 선택적인 문서별 `detail`을 가질 수 있다.

**FR-GRAPH-03** 그래프는 문서·스키마 버전을 구분해 LadybugDB에 저장해야 한다.
같은 문서 버전을 재추출하면 그 버전의 기존 행을 교체해야 한다.

**FR-GRAPH-04** 각 노드는 `label`, `type`, 문서 내 `id`를 가지며, 엣지는
`source`, `target`, `type`을 가진다. 엣지의 양 끝점은 같은 추출 결과의 노드여야
한다.

**FR-GRAPH-05** 노드 임베딩은 `label`과 `detail`을 합친 텍스트로 생성해야 한다.
추출과 임베딩은 별도 단계이며, 사용자는 이미 추출된 그래프에 임베딩을 다시
계산할 수 있어야 한다.

**FR-GRAPH-06** 사용자는 그래프 원자료와 현재 활성 스키마를 조회할 수 있어야
한다. 그래프가 없으면 HTTP 404를 반환한다.

**FR-GRAPH-07** 타입명은 그래프 DB 식별자로 사용되므로 영문자/밑줄로 시작하고
영문자·숫자·밑줄만 포함하는 식별자여야 한다. 안전하지 않은 타입명이나 존재하지
않는 노드를 가리키는 엣지는 저장하지 않고 오류로 처리한다.

### 3.4 GraphRAG 채팅

**FR-CHAT-01** 사용자는 역할과 콘텐츠로 구성된 전체 대화 이력을 전송해 채팅할
수 있어야 한다. 문서가 지정되지 않았거나 그래프가 없으면 일반 LLM 채팅을 한다.

**FR-CHAT-02** 활성 스키마와 그래프가 있으면 시스템은 질문과 스키마를 한 번의
분석 호출로 관련 노드 타입, 엣지 타입, 타입별 키워드를 결정해야 한다. 스키마에
없는 타입명은 제거한다.

**FR-CHAT-03** 각 관련 노드 타입은 다음 순서로 검색한다.

1. 해당 타입의 노드 라벨에 대한 키워드 부분 문자열 매칭
2. 매칭이 없으면 질문 임베딩과 해당 타입 노드 임베딩의 코사인 유사도 상위 5개
3. 임베딩도 없으면 해당 타입의 모든 노드

**FR-CHAT-04** 관련 엣지는 매칭 노드와 연결된 지정 타입을 우선 검색하고, 노드
매칭 자체가 없으면 지정 타입의 모든 엣지를 검색한다. 결과는 최대 5홉 범위로
확장할 수 있고 UI 설정의 기본값은 1홉이다.

**FR-CHAT-05** 검색 결과가 있으면 `Entities`/`Relations` 컨텍스트를 시스템
메시지로 삽입해 답변을 생성한다. 결과가 없으면 모델의 일반 지식으로 답하지
않고 `관련된 내용을 찾을 수 없습니다.`를 반환한다.

**FR-CHAT-06** GraphRAG 답변은 답변 내용 외에 결정된 타입과 검색된 관련 노드·엣지를
반환해야 한다. 프론트엔드는 타입 칩으로 필터를 토글하고 노드 칩으로 그래프의
노드를 하이라이트·자동 포커스해야 한다.

**FR-CHAT-07** 사용자는 ESC로 진행 중인 브라우저 요청을 취소할 수 있다. 이는
클라이언트 대기만 중단하며 서버의 LLM 호출을 취소하는 기능은 아니다.

### 3.5 화면 경험

**FR-UI-01** 화면은 설정/문서 목록, 채팅, 문서 원문, 온톨로지 그래프,
스키마·그래프 원자료 미리보기를 제공해야 한다.

**FR-UI-02** 그래프는 노드·엣지 타입별 색상 범례, 줌·팬·노드 드래그, 타입 필터,
콘텐츠 맞춤 및 리셋을 제공해야 한다. 스키마만 있으면 타입 기반 미리보기를
보이고, 추출 그래프가 있으면 실제 그래프를 우선 표시한다.

**FR-UI-03** 사용자는 채팅 Markdown 렌더링 여부와 GraphRAG 홉 수(1~5)를 설정할
수 있어야 한다. 채팅 기록은 브라우저 세션의 컴포넌트 상태에만 보관한다.

## 4. 비기능 요구사항

- **NFR-01 정확성:** 답변의 그래프 컨텍스트는 LLM이 임의로 만든 인용이 아니라
  실제 검색 결과에서 만들어져야 한다.
- **NFR-02 복원성:** LLM 연결 오류는 호출별 최대 2회 재시도하고, JSON 파싱
  오류는 HTTP 400으로 명시해야 한다.
- **NFR-03 보안:** 파일 경로는 basename으로 제한한다. `APP_PASSWORD`가 설정된
  배포에서는 인증되지 않은 API 요청을 차단하고 CORS preflight는 허용해야 한다.
- **NFR-04 운영성:** LLM·임베딩 호출은 OpenTelemetry span으로 추적 가능해야
  한다. 로컬 Jaeger가 설정되지 않아도 호출은 정상 동작해야 한다.
- **NFR-05 배포성:** 로컬은 Podman Compose로 실행하고, Render에서는 프론트엔드
  정적 서비스와 백엔드 웹 서비스를 분리한다.
- **NFR-06 데이터 지속성:** 백엔드의 `data` 디렉터리는 문서·스키마·그래프의
  영속 저장소이며 운영 배포에서는 Render 디스크에 둔다.

## 5. 상태와 오류 규칙

문서 상태는 `업로드됨 → 스키마 없음/있음 → 그래프 없음/있음`으로 이해한다.
스키마 생성·복사·도메인 적용은 새 버전을 활성화하고, 추출은 현재 활성 버전에
그래프를 만든다. 검증과 진화 제안은 기존 데이터를 즉시 변경하지 않으며,
진화 적용 API를 호출할 때만 스키마 변경을 저장한다.

- 존재하지 않는 문서·스키마·그래프·버전: HTTP 404
- 업로드 변환, LLM JSON, 잘못된 요청/식별자: HTTP 400
- 잘못된 공유 비밀번호 또는 토큰: HTTP 401
- DB 리셋: 모든 문서의 그래프를 삭제하고 스키마/원문은 보존

## 6. 성공 기준

다음 시나리오가 백엔드 테스트와 수동 UI 검증으로 확인되어야 한다.

1. 문서를 업로드해 Markdown 원문과 원본 파일명이 조회된다.
2. 스키마를 생성·복사·버전 관리하고 스키마 미리보기가 보인다.
3. 그래프를 추출·임베딩하고 타입 필터/범례/원자료 조회가 동작한다.
4. 특정 질문이 그래프 근거 답변과 관련 타입·노드 칩을 반환한다.
5. 관련 내용이 없을 때 명시적인 미찾음 메시지가 반환된다.
6. `APP_PASSWORD` 설정 여부에 따라 로그인 게이트가 켜지고 CORS 요청이 정상 동작한다.
7. LadybugDB 오류 시 리셋 후 원문·스키마로 재추출할 수 있다.

## 7. 현재 미지원 및 향후 범위

현재 제품은 다음을 보장하지 않는다.

- 사용자 계정, 역할/권한, 사용자별 데이터 격리, 만료 토큰, 로그인 rate limit
- 서버 저장 채팅 기록 또는 스트리밍 답변
- 스키마 타입과 추출 결과 타입의 의미 검증, LLM JSON 오류 자동 재시도
- 문서 청킹·토큰 예산 관리, 타입 테이블 garbage collection, 구형 JSON 그래프 마이그레이션
- 프론트엔드 자동화 테스트

이 항목들은 후속 제품 요구사항으로 별도 합의해야 하며 현재 PRD의 구현 계약으로
간주하지 않는다.
