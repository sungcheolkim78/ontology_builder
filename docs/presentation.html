PART 1

무엇을 만들었나
온톨로지 + GraphRAG 챗봇

문서를 그래프로 구조화하고, 질문마다 그 그래프에서 근거를 찾아 답하는 챗봇의 개념과 동작 원리를 먼저 살펴봅니다.

1부 · 01 · 문제 정의

왜 그냥 RAG로는 부족한가

일반적인 RAG (청크 검색)

문서를 문단 단위로 잘라 임베딩하고, 질문과 가장 비슷한 청크 몇 개를 그대로 프롬프트에 붙여넣습니다. "이 문서의 책임(responsibility)이 뭐야?"처럼 카테고리형 질문이나, 질문과 문서의 언어가 다른 경우 관련 청크를 놓치기 쉽고, 왜 그 답이 나왔는지 추적하기 어렵습니다.

이 프로젝트의 접근: 온톨로지 + GraphRAG

문서를 엔티티(노드)와 관계(엣지)로 미리 구조화해두면, 질문에 대해 "어떤 타입이 관련 있는지 → 그 타입의 어떤 인스턴스인지 → 몇 홉 떨어진 관련 정보까지"를 단계적으로 좁혀갈 수 있습니다. 답변에는 실제로 사용된 노드/엣지가 그대로 딸려 나와 근거를 확인할 수 있습니다.

1부 · 02 · 핵심 개념

온톨로지(Ontology)란?

온톨로지는 "이 문서 안에 어떤 종류의 사물(노드 타입)이 있고, 그것들이 어떤 종류의 관계(엣지 타입)로 연결되는가"를 정의한 스키마입니다. 회사 조직도를 예로 들면, 노드 타입은 Person, Team, 엣지 타입은 MANAGES, BELONGS_TO 같은 것입니다.

이 프로젝트는 두 단계로 나눠서 처리합니다 (app/ontology.py):

  • ① 스키마 생성 — LLM이 문서를 읽고 그 문서에 맞는 node_types / edge_types를 제안 (다른 문서의 스키마를 재사용도 가능)
  • ② 그래프 추출 — 그 스키마를 기준으로 실제 nodes / edges 인스턴스를 문서에서 뽑아냄
// schema.json — ① 스키마 생성 결과
{
  "node_types": [
    { "name": "Person", "description": "..." },
    { "name": "Requirement", "description": "..." }
  ],
  "edge_types": [
    { "name": "REQUIRES", "description": "...",
      "source": "Person", "target": "Requirement" }
  ]
}

// ② 추출된 노드/엣지 (LadybugDB에 저장)
{ "id": "p1", "label": "지원자", "type": "Person",
  "detail": "3년 이상 백엔드 경력 우대" }
{ "source": "p1", "target": "r1", "type": "REQUIRES",
  "detail": "동등한 업계 경력이 있으면 예외 인정" }
1부 · 02 · 핵심 개념

label만으로는 잃어버리는 정보 — detail

노드/엣지의 label과 type만으로는 "예외 조건이 있다", "정확한 수치는 이거다" 같은 문서 고유의 뉘앙스가 사라집니다. 그래서 추출 시 LLM에게 한두 문장의 detail 필드를 함께 채우도록 합니다.

예: Requirement 노드의 label은 "학위: PhD" 뿐이지만, detail에는 "동등한 업계 경력이 있는 경우 예외적으로 고려될 수 있음"이 들어갑니다. 이 한 줄이 없으면 "PhD 없이도 지원 가능한가요?" 같은 질문에 챗봇이 절대 답할 수 없습니다.

GraphRAG 컨텍스트로 조립될 때

Entities:
- 지원자 (Person)
- 학위: PhD (Requirement): 동등한 업계 경력이 있는
  경우 예외적으로 고려될 수 있습니다

Relations:
- 지원자 -[REQUIRES]-> 학위: PhD: (조건부)

이 텍스트 블록이 system 메시지로 주입되어, 모델이 근거를 갖고 답합니다.

1부 · 03 · 설계 원칙

좋은 온톨로지란? — "명사"가 아니라 "의미"를 모델링

나쁜 예 — Entity만 뽑기

"암 진단 확정 시 가입금액의 50%를 암진단보험금으로 지급한다"에서 단순히 명사만 뽑으면: 

암
가입금액
암진단보험금
50%

개별 단어는 남지만 "왜/어떻게 연결되는지"가 사라집니다.

좋은 예 — 관계까지 모델링

[보험상품]
  └─ hasCoverage → [암진단보장]
                     ├─ covers → [암]
                     ├─ triggers → [진단 확정]
                     └─ pays → [암진단보험금]
                                  └─ amount → [가입금액 × 50%]

Entity extraction → Relationship modeling → Business semantics 순서로 발전시키는 것이 핵심입니다.

  • 관계 이름은 동사로 — 관련정보 같은 명사 대신 hasCoverage/covers/excludes처럼 "동사"로 지으면 관계의 의미가 이름만 봐도 분명해집니다.
  • 처음부터 다 담으려 하지 않기 — hasPolicyHolderName, hasPolicyHolderAge… 식으로 세분화하면 타입 수백 개짜리 legacy가 됩니다. 핵심 개념 10~20개 + 실제로 근거 있는 관계만 우선 넣습니다.
  • "완전한가"가 아니라 "질문에 답할 수 있는가"로 검증 — "이 상품은 어떤 질병을 보장하는가?", "면책 조건은 무엇인가?" 같은 실제 업무 질문을 스키마/그래프로 표현해보고, 답할 수 없으면 빠진 타입/관계가 있는 것입니다.

자세한 원칙 10가지는 docs/ontology/ONTOLOGY_DESIGN_PRINCIPLES.md 참고 — 이 프로젝트의 스키마 생성 단계(app/ontology.py의 _SCHEMA_OUTPUT_INSTRUCTIONS)가 그중 "의미 중심 모델링", "동사 기반 관계", "과도한 세분화 방지" 원칙을 실제로 강제합니다.

1부 · 04 · 핵심 개념

왜 그래프DB인가 — LadybugDB

관계형 DB로 "이 사람과 2단계 이내로 연결된 모든 것"을 구하려면 재귀적인 JOIN이 필요해 복잡해집니다. 그래프DB는 노드-관계가 1차 시민이라, "N홉 이내의 모든 이웃"을 Cypher 한 줄로 표현할 수 있습니다.

app/graphdb.py가 backend/data/graph/graph.ladybugdb 연결을 단독으로 소유합니다 (지연 생성, 모듈 레벨 캐시). 설계상 특징:

  • 노드/엣지 타입 이름마다 Cypher 테이블 1개 — 모든 문서가 공유, 각 행은 source_document로 문서를 구분
  • 노드 id는 내부적으로 {stem}::{id}로 저장 (문서 간 충돌 방지), 반환 시 원래 id로 벗겨서 돌려줌
  • 타입 이름은 LLM 출력이므로 DDL/Cypher에 넣기 전 _validate_identifier()로 [A-Za-z_][A-Za-z0-9_]* 검증 (인젝션/구문오류 방지)
  • REL 테이블이 하나도 없는 상태(빈 DB)를 모든 그래프 함수가 별도로 처리 — 안 그러면 쿼리가 그냥 죽거나 조용히 빈 결과를 냄
-- expand_hops()가 실행하는 형태의 Cypher
MATCH (n)-[*0..2]-(m)
WHERE n.id IN $matched_ids
  AND n.source_document = $doc
RETURN DISTINCT n, m

-- 노드 테이블 DDL (타입마다 생성)
CREATE NODE TABLE Person(
  id STRING, label STRING, detail STRING,
  source_document STRING,
  embedding FLOAT[1536],
  PRIMARY KEY(id)
)
1부 · 05 · 핵심 개념

키워드로 못 찾으면 — 임베딩 유사도 폴백

"책임이 뭐야?"처럼 문자 그대로 추출할 키워드가 없는 질문, 또는 질문과 노드 label의 언어가 다른 경우 단순 문자열 매칭은 항상 실패합니다. 그래서 노드 타입별로 3단계 폴백을 순서대로 시도합니다.

  • node_embedding_text()가 label + detail을 임베딩 대상 텍스트로 정의 — 추출 시점(embed_nodes)과 질문 임베딩 (embed_query) 양쪽이 동일한 함수를 써서 두 벡터가 같은 기준으로 계산됨을 보장
  • 임베딩 모델은 OPENROUTER_EMBEDDING_MODEL (기본 openai/text-embedding-3-small, 1536차원) — 차원이 바뀌면 전체 재추출 필요 (Cypher FLOAT[N] 컬럼은 생성 후 너비를 못 바꿈)

2부 · 01 · 바이브 코딩이란?

AI와 대화하며 반복해서 만드는 개발 방식

미리 완벽한 설계도를 그리고 한 번에 구현하는 대신, "이런 기능이 필요해" → 나온 결과를 바로 보고 → "이 부분은 이렇게 고쳐줘"를 짧게 반복하며 코드를 키워가는 방식입니다. 이 리포 자체도 실제로 이렇게, 기능 하나당 커밋 하나씩 쌓으며 만들어졌습니다 (증거는 이 파트 끝의 2부 · 07에서).

이 방식이 끊기지 않고 잘 굴러가려면 아래 세 가지가 뒷받침돼야 합니다 — 다음 슬라이드들은 이 프로젝트의 아키텍처가 정확히 이 세 가지를 어떻게 채워주는지 순서대로 보여줍니다.

2부 · 04 · 프론트엔드 구조

App.vue = 상태 허브, 컴포넌트는 순수 props/emit

상태는 전부 App.vue에 있습니다: 선택된 문서, 노드/엣지 타입 필터, GraphRAG hop 수, 하이라이트된 노드 id 등. 컴포넌트 간 통신은 항상 App.vue를 한 번 거치는 "props 아래로, emit 위로" 패턴 — 별도 상태관리 라이브러리 없이도 다섯 컴포넌트가 정확히 동기화됩니다.

왜 "즉각적 피드백"인가 — Vite 핫리로드 덕분에 코드를 고치는 순간 브라우저가 갱신되므로, "이렇게 보였으면 좋겠다"는 요청을 바로 눈으로 확인하고 다음 요청으로 이어갈 수 있습니다.

2부 · 05 · 관측성

모든 LLM 호출을 Jaeger로 추적

LLM 호출은 느리고, 가끔 커넥션이 끊기고, 비용이 듭니다. telemetry.py의 invoke_with_telemetry()가 5개 호출 지점 (채팅 답변, 스키마 생성, 그래프 추출, 타입 분석, 키워드 추출)을 전부 감싸서 llm.{operation} span으로 기록합니다.

  • 모델명, 프롬프트/응답 길이, 성공 여부, 토큰 사용량을 span 속성으로 기록
  • 실제 프롬프트/응답 텍스트는 기록하지 않음 — 로컬 개발 환경 디버깅용 metadata만
  • ModelConnectionError(커넥션 끊김) 발생 시 고정 지연으로 최대 2회 재시도, 다른 예외는 즉시 전파
  • OTEL_EXPORTER_OTLP_ENDPOINT가 없으면(테스트 실행 등) no-op 트레이서로 자동 전환 — 항상 안전하게 호출 가능

왜 필요했나

실제로 OpenRouter 커넥션이 끊기는 문제를 겪은 뒤 추가됨. Jaeger UI(localhost:16686)에서 한 번의 채팅 요청이 실제로 몇 번의 LLM 호출로 구성되는지(최대 3회), 어디서 느려지는지, 재시도가 발생했는지를 그대로 확인할 수 있습니다.

2부 · 06 · 외부 서비스

이 프로젝트가 기대는 세 가지 서비스

코드는 로컬(podman-compose)에서도 돌아가지만, 그 코드를 보관/협업하는 곳, LLM을 실제로 호출하는 곳, 그리고 나중에 인터넷에 배포/서빙할 곳은 서로 다른 세 가지 외부 서비스입니다.

GitHub — 코드 보관소

소스 코드와 커밋 이력이 저장되는 곳 (github.com/sungcheolkim78/ontology_builder). "누가 언제 무엇을 왜 바꿨는지"가 커밋으로 남고, 브랜치/PR로 작업을 나눠 진행할 수 있습니다. 이 프로젝트를 Claude Code와 함께 만들 때도 매 기능이 커밋 단위로 GitHub에 쌓입니다 — 로컬 컴퓨터가 사라져도 코드는 안전하게 남는 백업 역할도 합니다.

OpenRouter — LLM 게이트웨이

여러 회사의 LLM(OpenAI, Anthropic 등)과 임베딩 모델을 하나의 API 키/엔드포인트로 호출할 수 있게 해주는 중개 서비스. chat.py / embeddings.py가 실제로 요청을 보내는 곳입니다. 모델을 바꾸고 싶으면 코드를 고칠 필요 없이 backend/.env의 모델 이름만 바꾸면 됩니다.

Render — (예정) 배포/호스팅

지금은 내 컴퓨터의 podman-compose로만 실행되어 외부에서 접근할 수 없습니다. Render는 코드를 인터넷 상의 서버에 올려 누구나 접속 가능한 URL로 서빙해주는 클라우드 호스팅(PaaS) 서비스로, 앞으로 FastAPI 백엔드와 Vue 프론트엔드를 여기에 배포할 계획입니다. 보통 GitHub 저장소를 연결해두면 git push만으로 자동 재배포됩니다.

2부 · 07 · 실전: 반복 개발의 증거

커밋 로그로 보는 "바이브 코딩" 한 사이클

2부 · 01에서 말한 세 가지(즉각 피드백 / 안전한 경계 / 관측)가 실제로 어떻게 맞물려 돌아갔는지, 이 리포의 실제 커밋 로그가 그대로 보여줍니다. 커밋 하나하나가 "요청 → 구현 → 확인"의 흔적입니다. 

256d387 Redesign ontology graph controls and left panel layout
7f74c05 Harden extraction and improve chat/DB efficiency
e3e5677 Add per-document manifest for original filename + status lookup
ed16814 Add LadybugDB reset button for WAL corruption recovery
469670b Add embedding-based similarity fallback for GraphRAG node matching
2761099 Add LLM call tracing, schema-aware keyword search, and test data isolation
   ...  기능 단위 커밋이 쌓여 지금의 구조가 됨

예를 들어 ed16814("LadybugDB 리셋 버튼 추가")는 실제로 WAL 손상으로 그래프 쿼리가 전부 실패하는 상황을 겪은 뒤, 화면에서 바로 재현/확인(Vue) → 원인 격리 후 graphdb.reset_database() 추가·pytest로 검증(FastAPI) → 배포까지 한 번의 대화 안에서 끝난 사례입니다.

2부 · 08 · 한계

알고 있는 한계 (일부)

  • 영속성 — 모든 데이터가 backend/data/에만 존재, 서버형 DB 없음, 사용자/세션 구분 없음
  • DDL 미청소 — 스키마를 바꿔 재추출하면 옛 타입의 테이블이 0행 상태로 영구히 남음
  • 인증 없음 — 로컬 개발 전용, 모든 엔드포인트가 열려 있음
  • 스트리밍 없음 — 채팅 응답은 한 번에 반환
  • 스키마/그래프 검증 없음 — LLM 출력의 키/리스트 구조만 확인, 타입 값이 스키마와 실제로 일치하는지는 확인 안 함
  • 구(舊) 문서의 임베딩 없음 — 임베딩 기능 이전에 추출된 문서는 벡터가 없어 (c) 전체-인스턴스 폴백만 가능
  • 프론트엔드 자동 테스트 없음 — 수동 또는 Playwright로 확인

전체 목록은 docs/SPEC.md의 "Known limitations" 참고.
