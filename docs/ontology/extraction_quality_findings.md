# 추출 품질 개선에서 얻은 지식 (2026-10)

처음 질문은 "완성된 온톨로지 스키마를 간략화하고, 그것이 평가 지표를 얼마나 올리는지 보이자"였다.
그 답을 찾으려고 평가 장치를 만들면서, 질문 자체가 바뀌었다. 이 문서는 그 과정에서 확인한 것,
바꾼 것, 조심할 것, 다시 하는 방법을 모아 둔다. 측정 방법의 상세는 `golden_set_evaluation.md`,
모든 실행의 숫자는 `eval_runs_table.md`(자동 생성), 번복하기 어려운 결정의 이유는 `docs/adr/`에 있다.

## 1. 한눈에

| 질문 | 답 |
|---|---|
| 병목은 검색인가 추출인가 | **추출.** 그래프에 정답 사실이 있는 문항의 94~100%를 검색이 가져온다 |
| 스키마를 간략화하면 정확도가 오르는가 | **아니오.** 타입 수를 약 30% 줄여도 이득이 없고, 다시 추출하면 오히려 줄어드는 경향(합 -7/83) |
| 가장 큰 레버 | ① 추출 그룹 크기(12,000→3,000자) ② 프롬프트의 커버리지 규칙 |
| 지표는 무엇을 믿나 | **답변 읽기**(검색 결과에 정답의 사실이 있는가). 증거 인용 기준은 보조 |
| 같은 설정을 반복하면 | 합계는 ±2~3문항, 문항별로는 약 25%가 갈린다. 그보다 작은 차이는 우연이다 |

정답 사실이 챗봇이 받는 컨텍스트에 있는 문항의 비율(답변 읽기, 올백 38문항 / 파워즉시연금 45문항):

| | 올백 | 연금 |
|---|---|---|
| 처음(12,000자 그룹, 기존 프롬프트) | 39% | 42% |
| + 그룹 3,000자 | 74% | 69% |
| + 커버리지 규칙 | **87%** | **73%** |
| 스키마 간략화 | 이득 없음 | 이득 없음 |

세 번째 줄까지는 서비스에 반영했다(`EXTRACT_GROUP_CHARS` 기본 3,000, `EXTRACT_COVERAGE_RULES`).

## 2. 측정에서 배운 것

이 대화에서 가장 많은 시간이 들어간 부분이고, 이후 실험의 신뢰도를 정했다.

### 2.1 읽기 네 가지와 무엇을 믿나

같은 검색 결과를 네 가지로 읽는다. 합치지 않고 나란히 보고한다(`retrieval_eval.score_golden_set`).

| 읽기 | 판정 | 비용 | 평가 |
|---|---|---|---|
| strict | 노드가 인용한 증거가 정답 구절과 겹침 | 없음 | 올백 5%에서 바닥이고, **같은 설정 두 번이 26%와 13%**로 크게 흔들림 |
| semantic | 노드·엣지 텍스트가 정답 구절과 코사인 0.75 이상 | 임베딩 | strict보다 낫지만 한 `detail`에 여러 사실이 압축되면 놓침 |
| **answer** | 검색이 돌려준 텍스트가 정답의 사실(`answer_facts`)을 담음. 수치·코드는 일치, 나머지는 두 글자 겹침 | 없음 | **기준으로 삼는다.** 결정적이고 챗봇이 실제로 답할 수 있는지에 가깝다 |
| judge | LLM이 같은 컨텍스트로 답할 수 있는지 판정 | 문항당 1회 | answer와 합계가 거의 같았고(13/13, 23/24) 문항별 일치 약 80%. 반복 노이즈는 못 잼 |

### 2.2 측정 자체에서 찾은 오류 (같은 일을 반복하지 않으려고)

1. **증거 인용만 보는 읽기는 낮게 잰다.** 노드가 사실을 말하면서 인접 문장을 인용하거나, 한 `detail`에 여러 사실을
   압축하면 miss로 셌다. 직접 열어 본 미해결 13문항 중 9개에서 수치가 이미 노드에 있었다.
2. **답변 읽기가 노드의 인용 증거를 텍스트에서 빠뜨렸다.** graphrag은 노드마다 `근거: <원문 인용>`을 컨텍스트에
   보여 주는데 읽기가 그것을 안 봤다. 고친 뒤 올백 v3 13→15, v7 25→28(잃은 문항 없음). 2026-10-16 이전 채점의
   답변 수치는 이 때문에 낮다(`eval_runs_table.md`의 `pre-fix` 표시).
3. **골든셋 생성이 문서의 일부만 봤다.** 질문 생성이 문서의 약 11%(24,000자 압축본)만 봐서 같은 부분에서
   문항이 나왔다. 호출마다 각 절의 다른 구간(창)을 보여 주는 배치(10문항씩)로 바꿨다.
4. **바이트와 글자 수를 혼동했다.** `wc -c`는 한글을 3바이트로 센다(올백 506,439바이트 = 224,227자).
5. **한 문항의 크기를 잊었다.** 올백은 한 문항이 2.6%p, 연금은 2.2%p다.

### 2.3 변동과 판단 규칙

- 같은 3,000자 설정을 두 번 추출하면 올백 답변 hit이 27과 28, 문항별로는 38개 중 약 7~10개가 갈린다.
  엄격 읽기는 26%와 13%였다.
- 그래서 정한 규칙: **±2~3문항 이내는 차이 없음.** 두 문서를 합쳐 판단할 때는 합계 +5 이상, 그리고 어느
  문서도 기준선보다 2문항 넘게 줄지 않을 것. 이 규칙으로 V1(커버리지)을 채택했다.
- 기준선은 한 번의 실행이 아니라 두 번 이상이 낫다. 연금은 아직 한 번뿐이다.
- 골든셋은 문서 앞쪽에 치우친다(증거가 문서의 20~40% 구간에 집중). attribute가 약 44%다.

## 3. 결과별 지식

### 3.1 검색은 병목이 아니다
그래프에 정답 사실이 있는 문항 중 검색이 가져온 비율: 올백 v7 97%, 연금 v3 97%, V1 적용 후 100%와 94%.
남은 miss는 거의 전부 "그래프에 사실이 없다"(추출 누락)다.

### 3.2 추출 그룹 크기
한 번에 모델에 주는 글자 수가 클수록 추출이 사실을 더 놓친다.

| 그룹 | 12,000자 | 6,000자 | 3,000자 | 1,500자 |
|---|---|---|---|---|
| 올백 답변 hit | 15/38 (39%) | 18/38 (47%)† | 27~28/38 (71~74%) | 24/38 (63%)† |
| 올백 추출 호출 | 16 | 32 | 57 | 104 |
| 연금 답변 hit | 19/45 (42%) | | 31/45 (69%) | |

† 증거 수정 이전 채점이라 낮게 잡혔다. 12,000→3,000자가 뚜렷하고 3,000→1,500자는 구분되지 않는다(무릎은 3,000자).
- 비용(연금): 호출 12→44회(3.7배), 소요 76→175초(2.3배), 입력 토큰 2.1배, 출력 2.6배.
- 같은 스키마, 같은 텍스트인데 청크 하나만 주면 놓친 구절의 47%가 돌아오고 12,000자 그룹은 6%였다.
- 그룹 크기는 청크를 쪼개지 못한다. 한 청크가 예산보다 크면 그 청크 하나가 한 그룹이 된다(§5, 이슈 #2).

### 3.3 스키마 간략화 (1단계 실험)
인스턴스가 한 자릿수인 꼬리 타입을 가까운 뼈대 타입으로 병합하고 사용되지 않은 엣지 타입을 삭제했다
(노드 타입 17→12, 13→9).

| | 기준 | (a) 다시 라벨링 | (b) 다시 추출 |
|---|---|---|---|
| 올백 | 28/38 | 28 | 24 |
| 연금 | 31/45 | 29 | 28 |
| 합계 | 59 | 57 (-2) | **52 (-7)** |

- 타입 수는 줄지만 노드·엣지 수는 거의 그대로다(706→705, 514→513). 정확도 이득도 크기 이득도 없었다.
- (b)의 감소는 변동(±2~3)에 가깝지만 두 문서에서 같은 방향이다. 해롭다고 단정하지는 못하고, 이득이
  없다는 것은 분명하다. 2단계(의미를 더 섞는 병합)는 돌리지 않았다.
- 미검증 가설: 작은 타입은 "그 타입 안에서 전부 가져오기/상위 5개"에 쉽게 걸려서 검색 색인 역할을 하고,
  큰 타입에 합치면 경쟁이 늘어난다. 연금 (a)에서 잃은 2문항으로는 확인되지 않았다.
- 병합 적용 모듈(`app.ontology.refinement`)은 남겨 두었다. 서비스는 쓰지 않는다.

### 3.4 남은 miss의 모습과 프롬프트
3,000자 기준선에서 남은 24개 miss(올백 10, 연금 14): 증거가 있는 청크가 1,000자 미만 16개, 정답에 수치 14개,
열거 5개. 짧은 조항 하나의 세부 규칙을 모델이 요지 한 줄로 줄여 버리는 모양이다(그룹당 노드 약 11개).

놓친 청크만 다시 추출하는 실험(대조군 = 현재 프롬프트 두 번):

| | 대조군 | **V1 커버리지** | V2 보충 패스 |
|---|---|---|---|
| 올백 (9문항) | 4, 3 | **6** | 4 |
| 연금 (13문항) | 5, 6 | **11** | 9 |

V1만 되살린 6문항 중 4개가 목록 질문(대조군이 놓친 목록 질문 전부)이었다. V2(1차 결과를 보여 주고 빠진 것만 더하게
하는 두 번째 호출)는 효과가 작고 호출이 2배라 접었다.

### 3.5 커버리지 규칙(V1)을 전체 문서에 적용

| | 기준선 | V1 | 얻음/잃음 | 노드 | 엣지 | 증거 인용 노드 |
|---|---|---|---|---|---|---|
| 올백 | 28 (74%) | **33 (87%)** | 6/1 | 706→968 | 588→845 | 56%→42% |
| 연금 | 31 (69%) | **33 (73%)** | 4/2 | 514→693 | 372→533 | 60%→49% |
| 합계 | 59 | **66 (+7)** | | +36% | +44% | |

유형별로 목록(올백 2→3/4, 연금 4→5/7)과 multi_hop(3→4/5, 5→6/6)이 올랐다. 비용은 연금 기준 출력 토큰
+49%, 소요 시간 약 2배. 챗봇 컨텍스트가 길어지는 영향은 재지 못했다.

### 3.6 그 밖의 관찰
- 같은 3,000자 추출 두 그래프를 합친 "사실이 있는 문항"은 31개(각각 27, 29)였다. 한 번 더 추출해 합치면
  5%p쯤 더 얻는 정도라 우선순위가 낮다.
- 문서마다 스키마의 타입 이름이 다르지만 뼈대는 같다(조항→규범→당사자·급부·조건·면책·서류, 정의어).
  `Provision`/`LegalProvision`, `Norm`/`LegalNorm`. 도메인 수준 정규 스키마의 여지가 있다.
- 챗봇 컨텍스트에는 노드의 라벨, 타입, `detail`, 인용 증거만 보인다. **`properties`는 보이지 않는다.** 그래서 내용은
  `detail`에 담겨야 하고, 속성만 늘리는 스키마 보강은 효과가 없다.
- 약한 유형: 목록, multi_hop, relation, boolean. 단일 사실(attribute)은 이미 잘 된다.

## 4. 서비스에서 바꾼 것

| 변경 | 위치 | 효과 / 비용 | 되돌리기 |
|---|---|---|---|
| 추출 전용 그룹 예산 `EXTRACT_GROUP_CHARS`, 기본 3,000 | `chunk_groups.py` | 정확도 +30%p, 호출 약 3.7배 | 환경 변수 |
| `EXTRACT_COVERAGE_RULES`를 `EXTRACT_PROMPT` 끝에 | `prompts.py` | 합 +7/83, 출력 토큰 +40~50%, 노드 +36% | 상수 삭제 (기준선 = 커밋 `6434cb3`의 프롬프트) |

| 골든셋 배치·창 생성, 덮어쓸 때 보관 | `preprocess/goldenset.py` | 문서 전체에서 질문 | |

`scripts/*`. 결정의 이유는 ADR 0001~0004.

## 5. 함정과 운영 지식

- **그래프 DB 버퍼 풀.** LadybugDB의 기본 풀은 256MB다. 버전이 쌓인 데이터 복사본(DB 217MB 이상)에서는 검색이
  `Buffer manager exception: Unable to allocate memory!`로 실패한다. 평가 스크립트는 1GB를 지정한다. 서비스도
  문서가 쌓이면 같은 증상이 날 수 있으니 `backend/.env`에 `LADYBUG_BUFFER_POOL_SIZE=1073741824`를 둔다.
- **큰 청크는 쪼개지지 않는다.** 안심종신 문서에는 310,127자 청크(문서의 60%, 별표와 코드 표)가 있다. 그룹 예산을 줄여도
  한 호출에 들어간다. 이슈 #2.
- **재개 캐시의 지문은 내용 기준이다.** 단계, 모델, 스키마 내용, 프롬프트, 추가 지시, 그룹 텍스트. 버전 번호는 키가 아니다.
  그래서 중단된 추출은 같은 명령으로 이어서 하고(`unfinished_copy`), 프롬프트를 바꾸면 자동으로 새로 계산된다.
  단, **잘못된 결과도 캐시에 저장된다.** 병합 단계에서 불완전한 노드를 거르는 이유다.
- **일시적 오류.** 제공자의 속도 제한(rate limit)이나 형식 틀린 응답이 가끔 나서 추출이 멈춘다. 같은 명령을 다시 실행하면
  이어서 한다.
- **모델.** 측정은 `google/gemini-3.7-flash`(`backend/.env`의 `OPENROUTER_MODEL`)로 했다. 모델을 바꾸면 이 문서의 숫자와
  직접 비교할 수 없다. 실행 기록(`run_*.json`, 점수 파일의 `run`)에 실제 모델이 남는다.
- **간략화 뒤에는 `FROM_VERSION`.** `make golden-density`는 활성 버전의 스키마를 복사한다. 활성 버전이 간략화된 것이면
  원래 스키마의 버전을 지정해야 한다.
- **쉘과 파일 이름.** zsh는 `$A:allbaek`의 `:a`를 경로 수정자로 읽는다(`"$A"`나 `${A}`로 쓴다). macOS의 한글 폴더 이름은
  분해형(NFD)이라 한글 리터럴 `glob`이 안 맞는다(직접 경로는 된다).
- **평가는 항상 `backend/data`의 복사본에서.** `make eval-data`. 스크립트가 실제 디렉터리를 가리키면 거부한다.
- **스크립트 파이썬.** 시스템 `python3`(3.9)가 아니라 `backend/.venv`(3.14)를 쓴다(Makefile이 그렇게 한다).

## 6. 다시 하는 방법

저장소 루트에서, 문서마다. `EVAL_STEM`은 문서 폴더 이름이다.

```bash
A='삼성올백(ALL100)종신보험(2601)(무배당,무해약환급금형)_약관_raw'

# 문서에 스키마가 없으면
make eval-schema EVAL_STEM="$A"                                   # 스키마 생성
make golden-generate EVAL_STEM="$A" EVAL_CONTEXT_CHARS=30000      # 골든셋 50문항 (창이 5개 이상이 되게 글자 수를 조정)

# 추출 그룹 크기별로 추출하고 채점 (결과는 backups/eval_runs/)
make golden-density EVAL_STEM="$A" GROUP_CHARS=12000
make golden-density EVAL_STEM="$A" GROUP_CHARS=3000 FROM_VERSION=<원래 스키마 버전>

# 이미 추출된 버전을 다시 채점 (읽기 규칙을 고쳤을 때)
make golden-score EVAL_STEM="$A" EVAL_VERSION=<n> EVAL_LABEL="메모"

# 놓친 청크만 다시 추출해 프롬프트 변형을 비교 (대조군 2번 + 변형 + 보충 패스)
make prompt-experiment EVAL_STEM="$A" REPORT=backups/eval_runs/<채점파일>.json VARIANT=<지시문 파일>

# 병합 매핑 시험
make eval-refine EVAL_STEM="$A" MAPPING=scripts/refinement_mappings/<파일>.json   # 적용 (호출 없음)

# 결과를 문서 표로 (backups/는 커밋되지 않으니 새 실행 뒤에 한다)
make eval-summary
```

변경을 판단하는 순서: ① 기준선을 두 번 이상 ② 한 번에 하나만 바꾼다 ③ 놓친 청크만 다시 추출해 싸게 거른다
(대조군 평균 +4문항, 잃은 문항 없음) ④ 전체 문서로 확인 ⑤ 변동(±2~3)을 넘고 합계 +5 이상일 때 채택.
호출 수와 시간의 어림은 `eval_runs_table.md`의 실행 기록에 있다(예: 올백 3,000자 추출 57회, 약 5~10분).

## 7. 열린 문제

- **챗봇 컨텍스트 길이.** 커버리지 규칙으로 노드가 36% 늘었다. 컨텍스트가 길어져 답변 품질·지연·비용에 주는 영향은 재지 않았다.
- **연금 기준선이 한 번뿐이다.** 연금의 V1 이득(+2)은 변동 안일 수 있다. 같은 조건으로 한 번 더 돌리면 확정된다.
- **남은 miss.** V1 적용 뒤 올백 5개, 연금 10개가 추출 누락, 연금 2개가 검색 누락이다. 올백의 목록·정확한 문자열·여러 조항 연결
  유형이 남아 있다.
- **큰 청크.** 이슈 #2. 청커를 고치면 안심종신 같은 문서에서도 그룹 크기 개선이 먹는다.
- **증거 인용 노드 비율 하락.** 56→42%, 60→49%. 근거 표시를 쓰는 화면이나 평가가 있다면 영향이 있다.
- **간략화.** 2단계는 시험하지 않았고, "작은 타입이 검색 색인 역할을 한다"는 가설은 미검증이다. 스키마를 사람이 읽기 쉽게
  줄여야 할 이유가 생기면 반복 실행으로 다시 잴 수 있다(약 600회 호출).
- **판정 읽기의 반복 노이즈**와 **골든셋의 앞쪽 편중**.
- **도메인 정규 스키마.** 문서마다 달라진 타입 이름을 하나로 모으는 일(`domain_schema_convergence.md`와 맞닿는다).
