# 골든셋 기반 스키마 평가 (Golden Set Evaluation)

작성: 2026-10-08. 첫 측정(파일럿)의 방법과 결과, 그리고 다른 컴퓨터에서 같은 작업을
이어가기 위한 자료 이전 방법을 기록한다. 관련 문서:
[`domain_schema_convergence.md`](domain_schema_convergence.md)(도메인 스키마 수렴과
내재적 지표), [`../../samples/README.md`](../../samples/README.md)(샘플 자료와 복원).

## 1. 왜 이것을 만들었나

"스키마 발견 → 생성 → 개선을 반복해 최적의 스키마를 찾는다"는 아이디어를 구현하기
전에, **스키마가 실제로 답변 품질의 병목인지**를 먼저 재야 했다. 기존 지표
(`evaluate_domain_schema`의 커버리지·타입 활용도·일관성·QA 성공률)는 스키마를 만든
LLM 계열이 스스로 매기는 "그럴듯해 보이는가"에 가깝고, 스키마가 질문에 답하는 데
도움이 되는지는 재지 않는다. 특히 QA 성공률은 GraphRAG가 실제로 답했는지가 아니라
`validate_ontology`의 LLM이 붙인 `answerable` 플래그다.

그래서 문서 전체에서 만든 **골든셋**(증거 인용문이 붙은 질문-정답)을 외부 기준으로
삼아, 챗봇이 쓰는 검색(`graphrag.search_graph`)이 정답 구절을 인용하는 노드·간선을
돌려주는지를 LLM 없이 결정적으로 채점한다.

### 반복 개선 루프의 설계 합의 (미구현)

심문(grilling)으로 합의한 방향이다. 루프 자체는 아직 만들지 않았고, 아래 첫 측정의
결과를 본 뒤에 만들지 정한다.

| 항목 | 결정 |
|---|---|
| 목적 함수 | 골든셋 검색 지표(1차). 내재적 지표는 보조 조건, 사람은 `NEEDS_HUMAN_REVIEW`에만 |
| 단위 | 도메인: 보정 문서 2~3개 + 평가 전용 유지 문서 1개 (유지 문서는 기준과 최종 후보 두 번만 평가) |
| 개선 근거 | 실패 주도: 검색이 증거를 못 찾은 골든 질문에서 스키마 변경을 제안. 제안이 목적 함수(골든셋 점수)와 같은 신호에서 나오고, 프롬프트가 질문 하나와 증거 구절 크기라서 문서 크기 제한이 없다. (기존 `validate_ontology`/`propose_evolution`은 문서 전체와 그래프 전체를 한 프롬프트에 넣어 `MAX_DOCUMENT_CHARS` = 100만 **자**를 넘는 문서에는 쓸 수 없는데, 현재 문서 4개 중 1개(2,156,965자)만 넘는다.) |
| 점수 | 결정적 검색 지표(반복마다) + LLM 답변 판정(최종 후보에만) |
| 채택 규칙 | 이전에 적중한 질문이 하나도 놓치지 않고(회귀 없음) 새로 적중하는 질문이 1개 이상일 때만 채택. 표본은 실행 시작 때 고정 |
| 변경 적용 | 반복 단위 묶음 적용 → 재채점 → 실패 시 되돌리고 묶음 축소 |
| 발견의 역할 | 시드 생성 때 한 번만 |
| 결과 | 비파괴: 모든 시도를 실행 기록으로 남기고 제안 스키마만 저장, 승격은 사람이 |
| 임시 그래프 | 공유 DB의 임시 stem(`__trial__…`), 끝나면 삭제 (용어: CONTEXT.md "Trial stem") |
| 예산 | 한 번에 수십 회 LLM 호출. 표본 질문의 증거 청크만 재추출하므로 점수는 같은 실행 안의 *상대* 값 (참고: 청크가 있는 세 문서를 통째로 한 번 재추출하면 청크 그룹 12 + 19 + 16 = 47회 호출) |

## 2. 골든셋

`app.preprocess.goldenset.generate_goldenset`이 문서 **전체**(청크가 아니라 `raw.md`)에서
만든다. 질문 생성 1회 + 답변 생성 1회, 총 LLM 호출 2회이고 질문 수와 무관하다.
청크로 만들지 않는 이유는 이것이 청크 기반 발견/스키마/추출 파이프라인을 *검증*하는
기준이기 때문이다(파이프라인의 맹점이 정답에 섞이면 안 된다).

레코드(`documents/{stem}/goldenset.json`의 `questions[]`)의 핵심 필드:

| 필드 | 뜻 |
|---|---|
| `question_type` | `entity` / `attribute` / `relation` / `multi_hop` / `list` / `boolean` / `unanswerable` |
| `answerable` | 문서에서 답할 수 있는가. 증거 인용문을 코드로 검증하지 못하면 `false`로 강등된다 |
| `answer_facts` | 정답을 이루는 원자적 사실(주어·술어·목적어) |
| `evidence[]` | `quote`(원문에서 그대로 복사한 인용문), `line_start`, `line_end` |
| (최상위) `source_sha256` | 골든셋을 만든 `raw.md`의 SHA-256 |

인용문은 생성 뒤 **코드로 원문 전체에 대해 다시 검증**한다(정확한 부분 문자열이어야
통과). 따라서 골든셋은 그것을 만든 바로 그 `raw.md`에 대해서만 유효하다. 문서를 다시
변환하면 해시가 달라지고 인용문이 어긋날 수 있다(채점기는 이런 질문을 `unscorable`로
분류한다).

## 3. 채점 방법 (`app.ontology.retrieval_eval.score_golden_set`)

답할 수 있는 골든 질문마다:

1. 질문을 챗봇과 같은 방식으로 검색한다 — `search_graph(질문, 스키마, stem, version, hops=1)`.
   "검색된 것"은 `related_nodes` + `related_edges`(홉 확장 포함)다.
2. **정답 구간**: 각 골든 `evidence`를 `raw.md`의 글자 구간으로 바꾼다. 골든셋이 기록한
   줄 범위 안에서 인용문을 찾으므로, 같은 문장이 두 번 나오는 문서에서도 질문이 가리킨
   위치로 정해진다(`evidence_spans`).
3. **인용 구간**: 검색된 각 노드·간선의 `evidence_text`가 `raw.md`에서 차지하는 구간.
   **저장된 `start_offset`/`end_offset`은 쓰지 않는다.** 청크 문서를 오프셋이 `raw.md`
   기준으로 정리되기 전에 추출했다면 오프셋이 라벨이 붙은 청크 그룹 텍스트 기준일 수
   있기 때문이다(CLAUDE.md의 오프셋 설명 참고). 인용문 자체를 믿는다.
4. **겹침 규칙**: 두 구간이 짧은 쪽의 **50% 이상** 겹치면 같은 구절을 인용한 것이다
   (`spans_overlap`). 노드가 정답 인용문보다 긴 문장이나 그 일부를 인용해도 인정되고,
   스치기만 하면 인정되지 않는다.
5. **재현율** = 인용된 정답 구간 수 ÷ 전체 정답 구간 수. 재현율 ≥ 0.5이면 **적중**.
   (`list`·`multi_hop` 질문은 증거가 여럿이라 "하나라도"는 관대하고 "전부"는 항목
   하나만 놓쳐도 0점이 되어 점수가 거칠어지므로 재현율로 보고한다.)

### 결과 분류

| 결과 | 뜻 | 의미 |
|---|---|---|
| `hit` | 정답 구절의 절반 이상이 검색 결과에 인용됨 | |
| `retrieval_miss` | 그래프에는 그 구절을 인용하는 노드가 있지만 검색이 돌려주지 않음 | 질문 분석(타입·키워드) 쪽 문제. 타입 설명 개선 등 스키마로 고칠 수 있는 경우가 많다 |
| `extraction_miss` | 그래프 어디에도 그 구절을 인용하는 노드·간선이 없음 | 해당 사실이 추출되지 않았다. 타입이 없어서인지(스키마 문제), 추출이 성기기 때문인지(추출 문제)는 이 분류만으로 알 수 없다 |
| `unanswerable` | 문서에 답이 없는 질문 | 점수에서 제외, 개수만 보고 |
| `unscorable` | 골든 증거가 현재 문서에서 더 이상 발견되지 않음 | 스키마의 적중도 누락도 아님. 점수에서 제외 |

요약(`summary`)에는 분류별 개수, 적중률, 평균 재현율, 질문 유형별 적중, **그래프에서
증거를 가진 노드·간선의 비율**, **같은 인용문이 문서에 두 번 이상 나오는 정답 구절 수**
(`repeated_passages`)가 들어 있다. 마지막 둘은 점수를 해석하는 데 필요한 한계 정보다.

### 알려진 한계

- **증거 필드가 비어 있는 노드는 인용으로 인정되지 않는다.** `evidence`는 추출 LLM이
  선택적으로 채우는 필드다. 첫 측정 그래프에서 노드의 39%, 간선의 35%만 채워져 있었다.
- **반복되는 문장.** 노드의 인용은 `raw.md`에서 *첫 등장 위치*로 고정(추출 규칙과 같음)
  되므로, 골든 정답이 같은 문장의 뒤쪽 등장 위치이면 그 노드로는 맞출 수 없다. 약관은
  같은 규칙을 여러 조항에 반복해서 쓰므로 실제로 일어난다. 그래서 "같은 사실이 그래프에
  있지만 다른 조항을 인용"하는 경우가 `extraction_miss`로 잡힌다(§5의 q001, q009).
- 표본이 작다(질문 20개). 한 문제가 5%포인트다. 점수는 추정치다.

## 4. 실행 방법

```bash
# 반드시 backend/data의 *복사본*을 가리킨다 (스크립트가 환경 변수 없이는 거부한다)
ONTOLOGY_DATA_DIR=/path/to/copy-of-backend-data \
  scripts/evaluate_golden_set.py "<문서 stem>_raw" [--generate 20] [--version 3] [--hops 1] [--json]
```

- **`ONTOLOGY_DATA_DIR`는 필수이고 기본값이 없다.** 이 스크립트는 그래프 DB를 열고
  `--generate`이면 `goldenset.json`을 쓴다. 백엔드 컨테이너가 떠 있는 상태에서
  실제 `backend/data`를 가리키면 DB가 손상될 수 있다. `scripts/backup_data.sh`로 스냅샷을
  만들어 복사본에서 작업한다.
- **비용**: `--generate N`은 LLM 호출 2회(질문 수 무관). 채점은 답할 수 있는 질문마다
  질문 분석 호출 1회. 첫 측정(20문항)은 총 약 22회, 2분 8초.
- **키**: `backend/.env`에서 `OPENROUTER_*` 항목만 읽는다. 출력하지 않는다.
- 채점 로직 자체는 `app.ontology.retrieval_eval.score_golden_set(stem, version, hops)`로
  쓸 수 있고, 백엔드 테스트(`tests/test_retrieval_eval.py`)가 가짜 모델과 임시 데이터
  디렉터리로 모든 분류를 검증한다.

## 5. 첫 측정 결과 (2026-10-08)

대상: `삼성올백(ALL100)종신보험(2601)(무배당,무해약환급금형)_약관` (파일 506KB = **224,227자**,
청크 227개 + 서문, 청크 그룹 16개), **스키마 v3**,
`legal` 문서 유형. 골든셋 20문항(답할 수 있는 19, 없는 1), `hops=1`.

| | |
|---|---|
| 채점 19문항 | **적중 4 · 검색 누락 0 · 추출 누락 15** (적중률 21%, 평균 재현율 21%) |
| 그래프 | 노드 355개 중 137개(39%)가 구절을 인용, 간선 245개 중 86개(35%) |
| 유형별 적중 | attribute 3/10, relation 1/3, boolean 0/1, entity 0/2, list 0/2, multi_hop 0/1 |
| 반복되는 인용문을 가진 정답 구절 | 4개 |
| 인용 구간의 분포 | 문서를 20등분했을 때 19개 구간에 걸쳐 있음 (특정 지역에 몰려 있지 않음) |

### 보조 진단: 그래프에 그 *의미*가 있는가

추출 누락 15문항에 대해 골든 정답과 의미상 가장 가까운 노드(라벨+상세의 임베딩 코사인)를
찾았다. 일회성 진단이며 아직 채점기에 들어가 있지 않다.

| 가장 가까운 노드와의 유사도 | 문항 수 | 해석 |
|---|---|---|
| ≥ 0.75 | 2 (q001 0.85, q009 0.75) | 사실은 그래프에 있다. 같은 내용을 다른 조항 위치에서 인용해서 엄격한 규칙이 누락으로 분류 |
| 0.60 – 0.74 | 6 | 주제는 맞는 노드가 있지만 질문이 묻는 세부를 담았는지는 불확실 |
| < 0.60 | 7 | 가까운 노드가 없다 (예: 선지급서비스특약의 세부 0.40, 살인죄 0.43, 보험계약대출 0.48) |

엄격한 적중률 21%는 하한이고, 사실이 있는 것까지 합친 상한 쪽 추정은 약 30%대다.
어느 쪽이든 절반 가까운 질문은 그래프에 해당 정보가 없다.

> **단위 주의.** 문서 크기는 바이트와 글자 수가 다르다. 한글은 UTF-8에서 글자당 3바이트라
> `wc -c`/`ls -l`의 값은 글자 수의 약 2.3배다. `MAX_DOCUMENT_CHARS`와 청크 그룹
> 예산(`MAX_CHUNK_GROUP_CHARS` = 12,000)은 **글자 수** 기준이므로 비용과 제한을 계산할
> 때는 `len(raw_text)`를 쓴다.

### 해석과 한계

- **청킹이 원인은 아니다.** 청크 텍스트가 `raw.md`의 95%(215,125자 / 224,227자)를 덮고,
  답할 수 있는 골든 질문 19개의 증거 인용문이 **전부** 청크 텍스트 안에 있다. 추출 누락은
  "그 텍스트가 어떤 청크에도 들어가지 못해서"가 아니다.
- **검색은 병목으로 보이지 않는다.** 검색 누락이 0이다. 단, 정답 구절을 인용하는
  노드가 있었던 질문이 4개뿐이라 이 결론은 약하다.
- **지배적 실패는 "추출된 내용이 질문의 세부에 닿지 않는다"이다.** 224,227자 문서에
  노드 355개(청크 그룹 16개당 평균 약 22개, 노드 1개당 약 630자)이고 정의·조항명·규범
  요약 수준이다. 질문은 그보다 세부를 묻는다. 같은 문서의 스키마 v1→v3 사이 노드 수는
  351→355로 거의 변하지 않았다. (그래프가 "극단적으로 성기다"고 단정할 수준은 아니다:
  밀도의 절대 기준은 아직 없다.)
- **아직 모르는 것**: 누락된 사실이 "현재 스키마로는 담을 수 없었던 것"인지 "원래 추출
  실행이 놓친 것"인지. 전자면 스키마 개선 루프의 여지가 있고, 후자면 추출 밀도(프롬프트,
  청크 크기, 출력 한도)를 고쳐야 한다.
- 한계: 질문 19개, 문서 1개, LLM 표본 1회. 골든셋은 문서를 예산에 맞게 압축한 뷰에서
  질문을 만든다(증거는 전체 원문에 대해 검증).

1. **채점기에 의미 규칙 추가** (LLM 비용 없음, 테스트 포함): 위 보조 진단을 정식 기능으로.
   반복 구절 문제를 완화하고 "사실이 그래프에 있는가"를 직접 보고한다.
2. **결정적 재추출 실험** (LLM 호출 약 10~15회): 추출 누락 질문들의 증거 청크 그룹만 현재
   스키마로 다시 추출해, 그 구절을 인용하는 노드가 나오는지 본다. 나오면 스키마는 충분했고
   원래 실행이 놓친 것이며, 안 나오면 스키마/프롬프트의 한계다.
3. 위 결과에 따라 반복 개선 루프(§1의 설계)를 만들거나, 우선순위를 추출 밀도 개선으로
   바꾼다. 이 결정은 되돌리기 어렵고 의외이며 실제 대안이 있었던 결정이므로, 결과를 본 뒤
   ADR로 남긴다("스키마 최적화의 목적 함수는 검증기 지표가 아니라 골든셋 검색 지표").

## 7. 자료 이전: 다른 컴퓨터에서 이어서 작업하기

`backend/data`는 git에서 제외되어 있어서(`.gitignore`) 문서·스키마·그래프는 저장소에
없다. 골든셋은 그것을 만든 정확한 `raw.md`에 묶여 있고 이 문서가 기존 샘플 압축
파일(`samples/*.tar.gz`)에 없었으므로, 둘을 함께 `samples/schema_eval/`에 올렸다.

| git이 옮기는 것 | 위치 |
|---|---|
| 문서 원문(`raw.md`, 506KB / 224,227자) | `samples/schema_eval/삼성올백(…)_약관.md` |
| 골든셋 20문항 | `samples/schema_eval/삼성올백(…)_약관.golden.json` |
| 복원 스크립트 | `scripts/unpack_samples.sh` (`samples/schema_eval/`도 처리) |

| git이 옮기지 **않는** 것 | 어떻게 얻나 |
|---|---|
| 청크(`chunks.json`) | UI의 청킹 버튼 (결정적, LLM 불필요) |
| 스키마 v1~v3, 발견 결과 | 발견·스키마 생성을 다시 실행하거나, 아래 스냅샷 |
| 추출된 그래프 (LadybugDB) | 추출을 다시 실행(이 문서는 청크 그룹 16개 = LLM 호출 16회)하거나, 아래 스냅샷. 이진 파일이고 WAL 문제가 있어 git에 넣지 않았다 |

### 절차 (새 컴퓨터)

```bash
git clone git@github.com:sungcheolkim78/ontology_builder.git && cd ontology_builder
git checkout dev
./scripts/unpack_samples.sh        # raw.md + goldenset.json 복원 (다른 샘플 15개도 함께)
cp backend/.env.example backend/.env   # OPENROUTER_API_KEY 입력
podman-compose up --build -d
```

복원된 `raw.md`가 골든셋과 맞는지는 해시로 확인한다.

```bash
shasum -a 256 "backend/data/documents/<stem>_raw/raw.md"
python3 -c "import json;print(json.load(open('backend/data/documents/<stem>_raw/goldenset.json'))['source_sha256'])"
```

두 값이 같아야 한다. 이 이전 흐름은 저장소를 임시 폴더에 새로 클론해 스크립트를
실행하는 방식으로 검증했다(올백 문서의 `raw.md`와 골든셋이 해시까지 일치하게 복원됨).

### 스키마·그래프까지 그대로 옮기려면

같은 v3 그래프로 평가를 재현하려면 `scripts/backup_data.sh`가 만드는
`backups/backend-data_<시각>.tar.gz`를 git 밖에서(복사, 클라우드 등) 옮겨 새 컴퓨터에서
`scripts/restore_data.sh <아카이브>`로 푼다. 스냅샷에는 문서·골든셋·스키마·그래프가 모두
들어 있으므로 위의 `unpack_samples.sh` **대신** 쓰는 별도 경로다. `restore_data.sh`는
`backend/data`가 이미 있으면 덮어쓰지 않고 거부하므로(`unpack_samples.sh`가 먼저
`backend/data/documents`를 만들어 버리면 거부된다) 둘 중 하나만 쓴다.

### 주의

- 이 저장소는 **공개**다. `samples/`에는 이미 삼성생명이 공개한 약관 원문과 골든셋이
  올라가 있고, 올백 약관도 같은 성격이라 그 관례를 따랐다. 공개하고 싶지 않은 문서는
  `samples/`에 넣지 말고 스냅샷으로만 옮긴다.
- 평가는 항상 `backend/data`의 **복사본**에서 한다(§4).
